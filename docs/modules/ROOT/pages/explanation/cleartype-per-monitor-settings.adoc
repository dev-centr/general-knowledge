= ClearType per-monitor settings
:navtitle: ClearType per-monitor settings
:description: Why Windows ClearType looks per-monitor in the UI but often applies globally—GDI vs DirectWrite/WPF registry paths, and what Better ClearType Tuner does.

Windows exposes two ideas that people conflate: *subpixel layout* (RGB vs BGR vs grayscale) and *which display that layout applies to*. The inbox ClearType Text Tuner (`cttune.exe`) asks which monitors to tune. Many third-party tools, including https://github.com/bp2008/BetterClearTypeTuner[Better ClearType Tuner], intentionally write one layout everywhere. Both behaviors are documented; neither matches the naive mental model of “each panel gets its own ClearType.”

== Verdict for mixed RGB/BGR desks

* Better ClearType Tuner does **not** offer per-monitor configuration. It sets the same RGB/BGR/grayscale choice on every connected display’s Avalon.Graphics keys **and** sets the desktop-wide GDI orientation via `SystemParametersInfo`.
* That is deliberate: the author found the monitor-specific registry surface unreliable in modern Windows and documented it in the app README and wiki.
* Using only `cttune.exe` does **not** guarantee independent RGB on the laptop panel and BGR on an external display. The tuner still writes the **global** `FontSmoothingOrientation` under `HKCU\Control Panel\Desktop`, which GDI text uses on all monitors. Per-display `PixelStructure` values help only apps that honor the Avalon/DirectWrite path for that `HMONITOR`.

Deeper HCI framing (UI that implies per-monitor honesty vs what renderers do): link:https://hci-nerdz.github.io/docs/hci-nerdz/cleartype-per-monitor.html[HCI Nerdz — ClearType per-monitor settings] and link:https://hci-nerdz.github.io/blog/cleartype-when-monitors-disagree/[essay].

== Two setting planes

[cols="1,2,2"]
|===
| Plane | Typical consumers | Scope

| Desktop / SPI
| Classic GDI text (and anything that follows `FontSmoothing*` under `Control Panel\Desktop`)
| **Session-global** — one orientation for the user, not per `DISPLAY*n*`

| Avalon.Graphics `\DISPLAYn`
| WPF ClearType knobs; DirectWrite paths that load monitor defaults
| **Named per display device** in the registry; runtime use still depends on the app calling `CreateMonitorRenderingParams` (or equivalent)
|===

=== Global GDI orientation

`SPI_SETFONTSMOOTHINGORIENTATION` / `SPI_GETFONTSMOOTHINGORIENTATION` expose RGB vs BGR as a single system parameter. Microsoft’s Win32 reference documents the values (`FE_FONTSMOOTHINGORIENTATIONRGB` / `…BGR`) without a monitor handle — unlike DirectWrite’s monitor-aware factory methods.

* API: https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-systemparametersinfoa[`SystemParametersInfo` — `SPI_*FONTSMOOTHINGORIENTATION`]
* Registry mirror commonly observed: `HKCU\Control Panel\Desktop` → `FontSmoothingOrientation` (`1` = RGB, `0` = BGR in practice for the tuner)

Independent reverse-engineering of `cttune.exe` steps (including which keys each wizard page touches): https://blog.yuo.be/2025/05/20/what-does-each-step-in-the-cleartype-tuner-do/[Reupen — What does each step in the ClearType Text Tuner do?] (2025). That write-up states that `FontSmoothingOrientation` / `FontSmoothingGamma` under Desktop normally affect **GDI on all displays**, while Avalon keys are the usual DirectWrite/WPF path — with the caveat that some DirectWrite apps ignore per-display parameters and use the primary only.

=== Per-display Avalon / WPF keys

Microsoft documents WPF ClearType registry values, including `PixelStructure` (`0` flat/grayscale, `1` RGB, `2` BGR), under display-named keys:

`HKLM\SOFTWARE\Microsoft\Avalon.Graphics\<display>` and user counterparts under `HKCU\SOFTWARE\Microsoft\Avalon.Graphics\<display>`.

* https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/cleartype-registry-settings[ClearType Registry Settings — WPF | Microsoft Learn]

If those values are absent, WPF falls back to system font-smoothing parameters (the global plane).

=== DirectWrite: support is opt-in per app

DirectWrite can create rendering params for a specific `HMONITOR`:

* https://learn.microsoft.com/en-us/windows/win32/api/dwrite/nf-dwrite-idwritefactory-createmonitorrenderingparams[`IDWriteFactory::CreateMonitorRenderingParams`]
* Conceptual how-to: https://learn.microsoft.com/en-us/windows/win32/directwrite/how-to-add-support-for-multiple-monitors[How to Add Support for Multiple Monitors]

Microsoft’s how-to is explicit: `CreateRenderingParams` always targets the **primary** monitor; apps must handle `WM_WINDOWPOSCHANGED`, call `CreateMonitorRenderingParams`, and `SetTextRenderingParams`. Pixel geometry enums include RGB, BGR, and flat:

* https://learn.microsoft.com/en-us/windows/win32/api/dwrite/ne-dwrite-dwrite_pixel_geometry[`DWRITE_PIXEL_GEOMETRY`]

So “Windows supports per-monitor ClearType” is true at the **API** layer and only sometimes true at the **application** layer.

== What Better ClearType Tuner actually writes

From the project’s own sources and docs:

. README caveat: per-monitor support “appears to be entirely non-functional in modern Windows, so this program sets all monitors the same.”
+
https://github.com/bp2008/BetterClearTypeTuner/blob/master/README.md
. Wiki investigation (Win10 1903 era): functional smoothing mostly tracked to `Control Panel\Desktop`; Avalon keys often showed “no apparent effect”; author believed monitor-specific keys “never mattered” and everything used the primary.
+
https://github.com/bp2008/BetterClearTypeTuner/wiki/ClearType-Investigations
. Issue discussion: choosing a monitor in the official tuner “doesn’t actually do anything” in the author’s experience.
+
https://github.com/bp2008/BetterClearTypeTuner/issues/11
. Implementation: on each change, `SetLegacyKeys()` loops **every** `Screen` device name and writes the same `PixelStructure` / gamma-related DWORDs under both HKLM and HKCU Avalon paths; RGB/BGR also goes through `SPI_SETFONTSMOOTHINGORIENTATION` (global).
+
https://github.com/bp2008/BetterClearTypeTuner/blob/master/BetterClearTypeTuner/MainForm.cs

Practical consequence: picking BGR in Better ClearType Tuner to “fix” an external BGR panel also stamps BGR onto the internal panel’s Avalon keys and onto the global GDI orientation. That part of community advice is accurate.

== What `cttune.exe` still does differently

The inbox wizard can write **different** `PixelStructure` (and related Avalon values) per `DISPLAYn` while still updating the **single** Desktop `FontSmoothingOrientation` for the run. Empirically mapped page-by-page by Reupen (linked above) and earlier by bp2008’s wiki.

So:

* Prefer `cttune.exe` when you care about Avalon/DirectWrite consumers that honor per-display keys **and** you accept that GDI remains one orientation.
* Prefer Better ClearType Tuner when you want a clear, working global RGB/BGR/grayscale + contrast control without the non-functional wizard pages (bp2008: pages 3–5 of the inbox tuner had no effect as of Windows 10 1903).
* Expect mixed-subpixel desks to stay imperfect under stock Windows text stacks; third-party renderers (for example MacType) exist precisely because inbox options are limited.
